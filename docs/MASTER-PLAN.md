## 1. Суть продукта
SaaS «сайт под ключ»: **клиент вводит URL → аудит → авто-исправление (клон с SEO-фиксами) →
публикация исправленной копии → отчёт со сметой до/после → оплата → доставка клиенту**.
Главная ценность — не советы, а **готовая исправленная копия сайта** + рост оценки 0→~100.

## 3. Что работает (проверено на реальных сайтах)
- **rimmebel.com**: 2528 стр, аудит 43→100, live на gh-pages `/rimmebel/`.
- **myarredo.by**: 100 стр, аудит 32→100, live `/myarredo-by/` (категории/подкатегории/инфо).
- Движок: BFS-обход по `<a>`, локализация всех ассетов, WebP (−66..71% веса), переписывание ссылок на демо + нормализация www, дедуп title/H1, canonical/og/JSON-LD, sitemap + image-sitemap + robots.
- **Page-derived уникальные тексты** (ниша-агностично): ключи/биграммы из самой страницы, без шаблонов, без гео-мусора (вырезан региональный свитчер поддоменов).
- **Качество SEO-блока** (последний цикл): нейтральный стиль (наследует сайт), текст всегда **до подвала**, таблицы видны (display-хардненинг), FAQ, перелинковка.
- **Картинки**: alt/lazy/WebP/srcset/width-height/говорящие имена + **локализация ассетов с поддоменов того же домена** (img.myarredo.by) + **фикс lazy-load** (data-src→src с удалением плейсхолдера) → 88/88 видны.
- Аудит до/после, **PDF-отчёт со сметой** (опт. 120₽/стр, SEO-текст 250₽/стр, аудит беспл.).
- Оплата: **каркас** `orders` (сумма на сервере) + `payment-create/webhook/order-status/orders-list` + гейтинг оптимизации (env opt-in). /admin/payments на реальных orders.
- WAF-сайты: доступ легитимно через **Googlebot UA** (`--ua`/`CLONE_UA`) — у myarredo nginx UA-allowlist.

## 5. Что нам нужно В ИТОГЕ (конечная цель)
Полностью **серверный, автоматический** пайплайн без ручного CLI:
клиент на сайте вводит URL → фоновый worker делает аудит+клон+исправления+рендер JS →
исправленная копия публикуется на **поддомене клиента/в хранилище** → отчёт+ZIP →
оплата ЮKassa → письмо с доступом. Админка на реальных данных.

- [ ] Прогон ещё 2-3 разнотипных сайта (CMS/SPA/самопис) для проверки универсальности.

### Фаза B — ПОДКЛЮЧАЕМ (потом, когда выходим в прод)
Порядок по приоритету ценности:
1. **Серверный worker движка** (Node-контейнер/VPS, НЕ edge — нужны cwebp/файловые ассеты). Переносим `site-clone.cjs` как есть. Решает п.2,3,4 разом.
2. **Headless-рендер на сервере** (Playwright/Puppeteer в том же worker) → закрывает JS-карточки (долг #1).
3. **Хостинг копий**: реальный поддомен клиента (DNS CNAME) или S3-совместимое хранилище + CDN, вместо gh-pages подпути. Параметризация base/canonical уже есть (`--prod`, `DEMO`).
4. **Оплата**: ключи `PAYMENT_PROVIDER=yookassa` + `YOOKASSA_SHOP_ID/SECRET_KEY` → провайдер включается, Checkout уже создаёт заказ и редиректит.
5. **Resend** на верифицированном домене (`MAIL_FROM`).
6. **Ингест** `ingest-fixed-pages.cjs` → реальный Supabase (`fixed_pages` ↔ `page_analysis`).
7. **Защита AI** (дневной cap) — частично есть, доконтролировать.
8. **CodeQL-долг** (отдельная задача).

## 7. Решение по JS-рендерингу (главный технический долг #1)
Варианты для товарных карточек/JS-контента:
1. **Серверный Playwright/Puppeteer** worker — рендерит DOM, отдаёт готовый HTML в клон. Предпочтительно (Фаза B).
2. **Feed/API сайта** (YML/JSON каталог, если есть) — самый дешёвый путь для e-commerce.
3. **Выгрузка/SSR от клиента** — когда есть доступ.
Локально (8 ГБ): полный Chrome виснет → **не блокируем продукт**, работаем со статикой + просим feed; полный JS-рендер откладываем на серверный worker или облачный браузер.
