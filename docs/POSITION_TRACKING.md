# Трекинг позиций

## Что это

Проверка мест домена в поисковой выдаче Яндекса и Google по списку запросов.
Данные берутся у внешнего поставщика выдачи: позицию нельзя вычислить на своей
стороне, её можно только запросить у того, у кого есть доступ к поиску.

До сентября 2026 года этот раздел был имитацией: `positionTracker.ts` генерировал
числа по хешу домена и `Math.random()`, «история» лежала в localStorage. Сейчас
генерации нет вовсе — если поставщик не настроен, проверка честно отказывается
работать и говорит, чего не хватает.

## Как устроено

```
UI (форма трекера) → checkPositions() → edge-функция positions-check
                                            ↓
                                     _shared/serp.ts → поставщик выдачи
                                            ↓
                              position_checks + position_results (БД, RLS)
```

- ключи поставщика лежат в секретах Supabase и в браузер не попадают;
- результаты пишутся под service-role, то есть пользователь не может вписать
  себе произвольную позицию;
- `position = 0` означает «в просмотренной выдаче (до `depth`) домена нет»,
  а не первое место.

## Настройка (нужен один поставщик из трёх)

В секретах проекта Supabase (Project Settings → Edge Functions → Secrets):

| Поставщик | Переменные | Заметки |
|---|---|---|
| XMLRiver | `XMLRIVER_USER`, `XMLRIVER_KEY` | дешёвый, Яндекс + Google, регионы РФ. Используется у нас |
| DataForSEO | `DATAFORSEO_LOGIN`, `DATAFORSEO_PASSWORD` | Яндекс + Google, счёт в долларах |
| SerpApi | `SERPAPI_KEY` | Google хорошо, Яндекс дороже |

Если ключи заданы у нескольких — выбрать конкретного можно переменной
`SERP_PROVIDER` (`xmlriver` / `dataforseo` / `serpapi`).

Дальше:

```bash
supabase db push                          # таблицы position_checks / position_results
supabase functions deploy positions-check # сама проверка
```

## XMLRiver: что важно знать

Проверено на живой выдаче 14.09.2026 (Google и Яндекс, запрос из каталога редукторов).

- **Размер страницы выдачи задаётся в кабинете**, а не в запросе:
  [Настройки сбора](https://xmlriver.com/queries/). По умолчанию приходит около
  десяти органических результатов за запрос. Наш код это учитывает и добирает
  глубину постранично (`&page=2`, `&page=3`, …), поэтому работает при любой
  настройке; если поднять размер страницы до ста, глубина 100 обойдётся в один
  запрос вместо десяти.
- **Стоимость считается за запрос к поставщику.** Проверка 20 запросов на глубину
  100 при стандартной настройке — это до 200 обращений. Баланс виден по адресу
  `https://xmlriver.com/api/get_balance/?user=<user>&key=<key>`.
- **Ошибка 500 «Выполните перезапрос» — штатная**: поисковик не ответил, надо
  повторить. Функция повторяет сама до трёх раз с нарастающей паузой.
- **Ошибка 15 — не сбой**, а «ничего не найдено»: такой запрос даёт позицию 0.
- Ответ идёт в формате Yandex Search API (расширенном). Органику отбираем по
  `<contenttype>organic</contenttype>`, чтобы реклама и колдунщики не сдвигали
  позицию вниз.
- Амперсанд в поисковом запросе передаётся закодированным (`%26`) — это делает
  `URLSearchParams`, отдельной обработки не требуется.

## Ограничения

- за одну проверку — не больше 50 запросов (функция работает синхронно);
  длинные списки надо разбивать;
- глубина проверки — 10–100 позиций;
- регион: для Google код страны (`ru`, `us`), для Яндекса номер региона (`213` — Москва);
- прокси-менеджер в проекте к трекингу позиций больше отношения не имеет:
  выдачу отдаёт поставщик, свои прокси для этого не нужны.
